# Deploy to Azure for intermittent classroom use

## Recommended shape

Use one Azure Container Apps Consumption app with two tightly coupled containers: Nginx serves the React app, and FastAPI handles `/api` and the live-quiz WebSocket. Both containers share one app origin, which keeps the existing cookie login and WebSocket routes working. The Azure web image is built with `API_UPSTREAM=127.0.0.1:8000`; Docker Compose keeps its default `api:8000` upstream.

Start at a total of 1 vCPU and 2 GiB for the app replica, `minReplicas: 0`, and `maxReplicas: 1`. The single replica matches the current API design: live-quiz WebSocket broadcasts are held in process memory, so multiple API replicas would not reliably deliver room events. Scale to zero when idle; the first request after a quiet period will have a cold start. Before a scheduled class, set the minimum to one and return it to zero afterward if you want a warm start.

The current live-quiz room limit is **32 players** (the presenter is separate). This setup can serve 40–50 ordinary concurrent visitors as a starting point, but one live room cannot accept 40–50 players until `MAX_ROOM` and the related team-balancing UI are raised. The existing local check covers 32 players plus a presenter; cloud capacity still needs a 50-client test before making a capacity promise.

## Cost fit for occasional use

- Container Apps Consumption grants each subscription 180,000 vCPU-seconds, 360,000 GiB-seconds, and 2 million HTTP requests free per calendar month. A 1 vCPU / 2 GiB replica running for 50 hours uses 180,000 vCPU-seconds and 360,000 GiB-seconds. Work beyond those monthly grants is billed, as can networking and logging services. See [Container Apps billing](https://learn.microsoft.com/en-us/azure/container-apps/billing).
- Azure Cosmos DB for MongoDB supports the lifetime free tier: up to 1,000 RU/s and 25 GB, if the free-tier option is selected when creating the account. It is limited to one free-tier Cosmos account per subscription and is not available with serverless capacity mode. Keep the app's two collections on shared throughput and monitor RU usage. See the [Cosmos DB free-tier limits](https://learn.microsoft.com/en-us/azure/cosmos-db/free-tier?tabs=cli).
- Azure for Students provides $100 credit for 12 months. Do not assume every free-account offer applies to a Student subscription: check the Student subscription's Free services page and estimated cost before creating PostgreSQL. If the PostgreSQL B1ms free benefit is not listed for this subscription, its compute and provisioned storage use the $100 credit. A Microsoft pricing example puts a B1ms server with 32 GiB storage near $16/month before offer adjustments, so $100 would cover roughly six months if it stayed on continuously; the actual Southeast Asia estimate depends on the subscription. Azure PostgreSQL compute can be stopped between long idle periods; storage and retained backups still cost money, and a stopped server automatically starts after seven days. See the [Azure for Students offer](https://learn.microsoft.com/en-us/azure/education-hub/azure-dev-tools-teaching/azure-students-program), [PostgreSQL pricing](https://azure.microsoft.com/en-us/pricing/details/postgresql/flexible-server/), and [Microsoft's pricing example](https://github.com/microsoft/azure-skills/blob/main/skills/azure-app-onboard/prepare/references/pricing-guide-services.md).
- The $100 Student credit expires after 12 months. If the student offer is not renewed or upgraded, deployed services are decommissioned, so export backups before the subscription end date. See the [Azure for Education FAQ](https://learn.microsoft.com/en-us/azure/education-hub/faq).
- Add a budget and cost alert before provisioning. Avoid Azure Monitor log ingestion beyond what is needed for troubleshooting, and do not create an Azure Container Registry if the public GitHub repository can use public GHCR images.

For this app, use Azure Database for PostgreSQL Flexible Server (small Burstable B1ms, no HA for the student prototype) and Azure Cosmos DB API for MongoDB with its free-tier option. Keep both databases in the same nearby region as Container Apps where the Student subscription permits it. PostgreSQL is the relational source of truth; MongoDB stores the lesson and question documents.

## Provisioning order

1. Open Azure Portal **Cloud Shell** (Bash), which already has Azure CLI, or install Azure CLI locally and sign in with `az login`. Confirm the subscription is **Azure for Students** (not the separate Students Starter offer), check the remaining credit, select a region close to Thailand that offers Container Apps, PostgreSQL Flexible Server, and Cosmos DB, then create one resource group.
2. Create Cosmos DB for MongoDB with the free-tier discount enabled and provisioned throughput, not serverless. Use one shared-throughput database at no more than 1,000 RU/s and keep the account within 25 GB. Copy the Mongo connection URI from the portal.
3. Create PostgreSQL Flexible Server in the same region. Start with Burstable B1ms, no high availability, small storage, TLS required, and the shortest backup retention that suits this classroom project. Confirm the Azure portal's estimate and Student free-service eligibility before selecting Create. Copy a connection URI using the `postgresql+psycopg` SQLAlchemy scheme and `sslmode=require`; URL-encode special characters in the password.
4. Create an Azure Container Apps environment on the **Consumption** workload profile. Avoid a dedicated workload profile and private VNet for the first budget prototype. Restrict database network access to the Container Apps environment's outbound addresses where supported; do not leave database firewall access open to the internet. Both database connections must use TLS. HTTP ingress supports WebSockets, which this app uses for Live Quiz; Azure documents a 240-second request timeout, so validate a full quiz and the client's reconnect behavior in the cloud.
5. Enable GitHub Actions for the repository. The first successful workflow run builds and publishes immutable SHA-tagged web and API images to GHCR. Set both packages to public so Azure can pull them without adding paid registry infrastructure. Image names follow `ghcr.io/<owner>/<repo>-web:<sha>` and `ghcr.io/<owner>/<repo>-api:<sha>`.
6. Copy `infra/azure/migration-job.example.yaml` to `infra/azure/migration-job.local.yaml` (ignored by Git). Replace the API image tag and both database connection strings, then create a manual migration job in the Container Apps environment with `az containerapp job create --name astromerical-migrate --resource-group <resource-group> --environment <environment-name> --yaml infra/azure/migration-job.local.yaml`. Start it with `az containerapp job start --name astromerical-migrate --resource-group <resource-group>` and confirm the newest execution succeeds before creating the web app. The job applies Alembic migrations and seeds the Mongo and PostgreSQL data.
7. Copy `infra/azure/containerapp.example.yaml` to `infra/azure/containerapp.local.yaml` (ignored by Git). Replace the image values and database secret values. The app hostname is generated during creation, so leave the allowed-origin placeholder for now. Create the app with `az containerapp create --name <app-name> --resource-group <resource-group> --environment <environment-name> --yaml infra/azure/containerapp.local.yaml`. Then read its hostname with `az containerapp show --name <app-name> --resource-group <resource-group> --query properties.configuration.ingress.fqdn --output tsv` and set `ALLOWED_ORIGINS` on the `api` container to `https://<that-hostname>` in the Azure portal or with `az containerapp update --name <app-name> --resource-group <resource-group> --container-name api --set-env-vars ALLOWED_ORIGINS=https://<that-hostname>`.
8. Check `/api/health`, guest sign-in, account sign-in, the chart, tutor fallback, and a live quiz with several browser profiles. Confirm WebSocket connections stay on the same app hostname. Add an OpenRouter key only if AI-generated tutor and chart readings are wanted; the key belongs in Container Apps secrets, never in the web image or GitHub repository.
9. Turn on Azure deployment in GitHub only after the initial app works. Set the repository Actions variable `AZURE_DEPLOY_ENABLED` to `true`, variables `AZURE_RESOURCE_GROUP`, `AZURE_CONTAINER_APP_NAME`, and `AZURE_MIGRATION_JOB_NAME=astromerical-migrate`, and secrets `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, and `AZURE_SUBSCRIPTION_ID`. Configure an Entra federated credential with issuer `https://token.actions.githubusercontent.com`, subject `repo:<owner>/<repo>:ref:refs/heads/main`, audience `api://AzureADTokenExchange`, and grant its service principal Contributor on this resource group. The workflow uses OIDC, tests the app, publishes new SHA-tagged images, runs the database migration job to completion, then updates the API and web containers.

The migration job owns its own two database secrets, so enter the same connection strings there and in the app configuration. Its image and job definition are updated by GitHub Actions on each deployment. The migration job is safe to rerun: Alembic does nothing when already at head, and the deterministic seed uses upserts. Continue to make schema changes additive and verify the job succeeds before the app image is updated.

## Operating the app only during classes

Container Apps scales down automatically after traffic stops. PostgreSQL does **not** stop when the web app scales to zero. For the cheapest operation, leave PostgreSQL running if the workload is regular and covered by the Student credit/free allowance; if classes are separated by long idle periods and the portal shows a meaningful compute charge, stop PostgreSQL after the class and start it before the next one. Keep Cosmos DB within its free tier. Do not stop PostgreSQL while users are active, and remember stopped servers still incur storage/backup charges.

For manual class windows, start PostgreSQL before the class, set the app to one warm replica, then reverse both settings after the class:

```bash
az postgres flexible-server start --resource-group <resource-group> --name <postgres-server>
az containerapp update --name <app-name> --resource-group <resource-group> --min-replicas 1
# After class, once all players have left:
az containerapp update --name <app-name> --resource-group <resource-group> --min-replicas 0
az postgres flexible-server stop --resource-group <resource-group> --name <postgres-server>
```

If you use Azure Cloud Shell to create the app, upload the two ignored `*.local.yaml` files for the initial setup, then delete the copies from Cloud Shell and your computer after Azure has stored the secrets.

The API currently runs one Uvicorn worker and one app replica. Keep `maxReplicas` at one for live quizzes. If cloud testing shows slowdowns, first increase the app to 1.5 vCPU / 3 GiB and rerun the load test. To scale API replicas horizontally, first move WebSocket room events to a shared broker and test reconnects and scoring across instances. Azure documents [HTTP/WebSocket ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview), [scale-to-zero behavior](https://learn.microsoft.com/en-us/azure/container-apps/scale-app), and [sidecar resource limits](https://learn.microsoft.com/en-us/azure/container-apps/containers).

## First release checklist

- Verify the final HTTPS origin is the only value in `ALLOWED_ORIGINS`; set `COOKIE_SECURE=true`.
- Confirm database TLS, firewall rules, backups, and a restore test.
- Confirm the Container App returns `200` from `/api/health` and Nginx can reach the API over `127.0.0.1:8000`.
- Run a 50-client cloud load test, including a 32-player Live Quiz room, presenter screen, reconnects, and simultaneous answers. Raise the room limit only as a separate tested change.
- Set Azure budget alerts and check Azure for Students credit weekly during the first month.
